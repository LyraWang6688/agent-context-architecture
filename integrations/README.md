# integrations/ · 集成

> 这是一个**定义文件**，不是内容文件。架构先搭，内容后写。

## 这部分是什么

**第三方系统是怎么运作的、有哪些约定和坑。**

## 回答什么问题

> 「这个外部系统本身是什么样子的？」

## 为什么它要建文件夹（而 preferences / memory / global 不用）

**因为它要分不同的生态。**

```
integrations/
├── feishu.md        飞书 Open API
├── doubao.md        豆包工作 MCP
├── workbuddy.md     腾讯 WorkBuddy MCP
└── （以后每接一个新生态，加一份）
```

**一个生态一份，各自独立。**各生态的量、内容、更新节奏都不一样，
合在一起会让"只想接豆包"的 agent 吞下另外两家的全文。

## 收什么

每个生态里只装三样：

1. **怎么进去**——认证 / token / 入口
2. **怎么用对**——踩了会**静默出错**的关键约定
3. **哪里翻过车**——pitfalls

## 不收什么

- ❌ **不抄官方文档**——文档会更新，抄一份必然过期。
  > **不抄就不会过期。**需要的细节一律外链。
- ❌ 不写我们自己的工程规范（那是 `global`）
- ❌ 不写会频繁变化的状态

## 三条硬规矩

### 1. 只写"用它的 agent 会踩到的和必须知道的"

不写它自己的 API 全书。判据：**这条内容，是不是"不看就会做错"？**
不是 → 外链，不复制。

### 2. 作者是别人，靠验证定对错

这一层的内容**不是我们定的**，是第三方定的。
所以每条要能回答：**谁验的、什么时候验的。**
过期的知识比没有知识更危险——**旧经验会被当成当前事实。**

### 3. pitfalls 只追加，不重写

描述性内容（认证怎么做）会整篇作废重写；
**教训不会**——系统修了 bug，这条坑"失效"但不该删，它变成了历史。

### pitfalls 准入（三条全中才算）

1. 有陷阱——有能力、不马虎的人也会自然掉进去
2. **静默失败**——不报错，或报错指向错误方向
3. 独立可行动——不依附任何一条指令就能用

> 第 2 条筛掉"会准确报错"的东西（那种 agent 自己会改，不算坑）。
> 第 3 条筛掉"原因"——**原因依附于指令，不是坑。**

## 还有一个跨生态的问题

**"怎么调查一个陌生系统"这件事，不属于任何一个生态。**

（比如：怎么确认一个桌面 App 支不支持 MCP、官方文档在不在 App 里、
文档写的配置路径和实际用的不一致怎么办。）

放在某一个生态的文件里，其他生态就用不到。
**但要不要给它单独一份文件、还是放进本文件——待定。**
